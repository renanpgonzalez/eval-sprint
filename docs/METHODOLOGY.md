# Methodology: what the numbers mean, and what is not claimed

A short page for the engineers who will own the eval and the reviewers who have to trust it. The interfaces are in [ARCHITECTURE.md](ARCHITECTURE.md); the numbers quoted here were measured in the project's own simulations. The gate tables are reproduced by `python scripts/gate_numbers.py` (and, for every size, in `orchestration/2026-09-29_kit-v0.2/cycle3/eval-scientist-gate/gate_rates.md`); the calibration and judge simulations are in `orchestration/2026-09-29_kit-v0.1/` (cycle-1 critic material) and `orchestration/2026-09-29_kit-v0.2/cycle3/eval-scientist-judge/`. The exact enumerations behind the false-alarm, detection, crash and baseline-lottery figures are in `scripts/gate_numbers.py` (and, computed a second way, `compare.expected_gate_rates` for one attempt per case and `compare.expected_gate_rates_protocol` for the repeat protocol of a run, which `evalsprint noise` prints from 20 repeated cases on); `orchestration/2026-09-29_kit-v0.2/cycle4/` holds the scripts and logs of the last round. This page describes evalsprint 0.2.

## 1. Outcome model: pass, fail, error

Every case ends in one of three outcomes. **`error`** means the run could not judge it: the target raised, or any judge that applies returned an error after its own retries (`error_source` says which). Within one run, errors are not counted as quality failures: `n_scored = n_passed + n_failed`, the pass rate and its Wilson interval are computed on the scored cases only, and `error_rate = n_errors / n_cases` reports the damage separately. A run whose error rate is above `max_error_rate` (default 5%) is **unhealthy**: `run` exits 3, and `baseline` and the CI gate refuse to use it. The reason is practical: before this rule, a judge API outage looked like a 90-point quality collapse and could even be committed as the baseline. When two runs are **compared**, the two kinds of error are treated differently, because they mean different things: a *judge* error (or an error that is already in the baseline) says nothing about the change and is left out, while a *target* error on a case that passed in the baseline means the feature crashed where it used to answer, and counts as a failure. Without that rule a change could turn four regressions into four crashes, keep the pass rate above the limit and pass (the critic's scenarios W8 and W10 did exactly that). A target call that raises is first tried again inside the run (`target_retries`, default 1; the retry is paid for and counted as `n_target_retries`), so a transient 429 does not become an `error`. A run whose target is the scaffold's offline stub, or whose LLM judge runs on the `mock` provider, carries `summary.placeholder: true`: it proves the pipeline runs and measures nothing, so `baseline` refuses it without `--force` and `compare` warns when the baseline is one.

## 2. The regression gate

`compare` pairs cases by `case_id`, only when the `case_sha` (a hash of every field of the case except its `id`: input, reference, expected behavior, tags, checks, `must_include`, metadata) matches and neither run errored. Cases that disappeared or were edited are counted and, by default, block the change (`max_removed_cases: 0`, `max_changed_cases: 0`): deleting the cases you fail, or editing them, is the cheapest way to pass a gate. The same goes for the judges: `summary.judges_sha` hashes the judge block, the rubric texts, `pass_rule`, the source of the file of every `custom` judge and every file in its `data_files`, and a different sha is a regression reason (`allow_judge_changes: false`), because a more lenient judge lifts every pass rate. It does not see the code a custom judge imports from elsewhere, the code of the target (`run --resume` does hash the adapter file, the gate does not), or a hosted model that changes behind the same name. (Upgrading from v0.1 changes `judges_sha` of every suite with a custom judge, because the code used to be outside it: refresh that baseline in a reviewed PR, see CHANGELOG.md.) The evaluation protocol is held to the same standard: the `repeat` protocol of the two runs (`n` and `per_tag`, the older `tags` spelling read as its `per_tag` form) must be identical (`allow_repeat_change: false`), because a bigger majority vote is an easier gate, and a different version of the kit, patch included, is a warning (a reason with `require_same_kit_version: true`). Errors are handled by kind: a target error on a case that passed in the baseline is paired as a failure (it feeds the drop, the McNemar counts, the by-tag rates and the critical tags, so a crash on a critical case blocks like any other critical flip); a judge error, a baseline error and a crash on a case that already failed are left out and named in a warning; a *critical* case that passed in the baseline and whose candidate judge errored blocks the change (fail closed), since it could not be verified. The absolute rules cannot be diluted by appending easy cases: `min_pass_rate` is checked on the whole candidate run and on the cases that also exist in the baseline, and `max_error_rate` on the whole run and on the candidate's errors among the baseline's cases. What this costs: a crash adds to the false-alarm rate (exact for the v0.2 rule at 5% noise: a target that crashes on 1% of the cases takes it from 10.6% to 14.7% at 45 paired cases, from 7.1% to 11.1% at 100 and from 4.0% to **8.0%** at 200, and a crash on 5% of the cases, the most a healthy run may have, takes it to 34.6%, 36.2% and 42.4%), and two crashes in 45 cases still pass below the 3-case floor, exactly like two wrong answers. Retry provider errors inside the adapter; `target_retries` covers one more. A crash in one attempt of a repeated case is counted too: `attempt_error_rate` is held to `max_error_rate` like the case-level rate, and a case that passed in the baseline and crashed in some attempt of the candidate is named in a warning even when its majority verdict is pass.

`max_pass_rate_drop: auto` is **one rule for every number of paired cases** `n` (version 0.1 switched rules at 150 cases, which made detection fall at the switch). With `b` cases that went pass to fail and `c` that went fail to pass, the candidate fails when BOTH hold:

- the **net loss** `b - c` is at least `max(3, ceil(n / 50))` cases: never on fewer than 3, and from 150 cases on never on less than 2 percentage points;
- a **one-sided exact McNemar test** rejects "no worse" at `alpha(n) = 0.0575 + 0.1925 / (1 + (n / 85)^4.5)`. Only the discordant pairs carry information. Under "no change" `b` is Binomial(b + c, 1/2) given `b + c`, and the one-sided p-value is P(X >= b). One-sided because the question is "did it get worse", not "did it change". A small suite has little data and gets a generous alpha (0.24 at n = 45, 0.12 at n = 100); a large one a strict alpha (0.0575 in the limit). The detection figures come from a model in which a true drop hits a random share of the cases; a model in which it hits an exact number of cases gives figures from 2.4 points lower to 7.9 points higher on the sizes that were compared (30 to 300 cases), so read them as "about".

Because the rule is a finite set of `(b, c)` pairs for each `n`, every rate quoted below is an exact sum, not a simulation. Measured behavior (baseline pass rate 80%, independent per-case flips of 5% in each run, an identical system): false alarms of **10.6%** at n = 45, 7.1% at n = 100 and 4.0% at n = 200, at most 4.3% for every n from 150 to 500; a true 10 p.p. drop is caught **67%, 80% and 93%** of the time at 45, 100 and 200 cases, and a 5 p.p. drop 39%, 42% and 51%. The curve is not flat and not perfect: false alarm peaks at 12.3% near n = 54 (15.1% with 10% noise, same size), and between 60 and 149 cases the rule is a different trade from v0.1, not a strict improvement: the rule of v0.1 had a lower false alarm **and** a higher detection of a 10 p.p. drop at 84 of the 90 sizes at 5% noise (every size but 60 to 62 and 78 to 80; at 10% noise v0.2 is the stricter rule and blocks less often), so the honest claim is "one smooth rule without a cliff at 150", not "better at every size" (see the tables and the comparison in `evalsprint/templates/github/README.md`, section 9). What it removes is the step at 150 and the cliffs: the detection of a 10 p.p. drop never falls by more than 2.6 p.p. as the test set grows from 30 to 500 cases (v0.1: up to 12.4 p.p.). A number in `max_pass_rate_drop` (0.03 = 3 p.p.) is a fixed limit, as before. `python scripts/gate_numbers.py` recomputes the tables. **Critical tags** are deliberately not statistical: one pass-to-fail flip fails the gate, so repeat those cases (below).

**The committed baseline is one noisy draw.** The figures above average over every baseline you could have drawn. Given the baseline that was committed, the false-alarm rate of all later pull requests is exact and varies a lot: at 5% noise and a true pass rate of 80%, the probability that it exceeds 15% is 28.8% at 45 paired cases, 14.0% at 100 and 7.2% at 200 (median baseline 7.0%, 1.3% and 0.6%; 95th percentile 42.9%, 31.3% and 22.6%). So "the false alarm is 4% at 200 cases" is true on average and not a promise about your baseline, and a pull request that is blocked again and again without a change in the feature is a reason to look at the baseline. Two things shrink the lottery: a baseline made with the same `repeat` protocol as the pull requests (a majority of three attempts has a flip probability of 0.725% instead of 5%, and the chance of more than 15% falls to under 0.15% at all three sizes), and more cases. Re-drawing the baseline until the pull requests pass is not a fix: it is the same as choosing the reference to pass.

**The gate in one paragraph.** The gate compares each change with the committed baseline on the same cases. It blocks the change only when the cases that went from pass to fail outnumber those that went from fail to pass by at least max(3, n/50), and a one-sided exact sign test (McNemar) says that such an imbalance would be unusual by chance. The test is lenient on small suites (alpha about 24% at 45 cases, 12% at 100, 7% at 150) and tightens to about 5.8% beyond roughly 300 cases. It is a noise-aware threshold, not a guarantee. With 5% random noise per case and one attempt per case, an unchanged system is blocked about 11% of the time at 45 cases, 7% at 100 and 4% at 200, averaged over possible baselines; for one committed baseline the rate can be far higher or lower. A 10-point drop is caught about 67%, 80% and 93% of the time, and a 5-point drop only about 39%, 42% and 51%. Cases tagged critical sit outside this statistical rule: any single pass-to-fail flip blocks, so they must be repeated 5 times.

**What that paragraph leaves out** (the rest of this section and section 3 have the numbers and how they were computed). The rates above are rounded: exactly, an unchanged system is blocked 10.6%, 7.1% and 4.0% of the time at 45, 100 and 200 cases, and a 10 point drop is caught 66.6%, 79.7% and 92.7% of the time. The false alarm is not flat: it peaks at 12.3% near 54 cases (15.1% with 10% noise), and between 60 and 149 cases the rule of v0.1 had a lower false alarm and a higher detection at 84 of the 90 sizes at 5% noise (every size except 60 to 62 and 78 to 80 cases; at 10% noise v0.2 is the stricter rule and blocks less often: over those sizes the mean false alarm is 8.3% against 11.5% and the mean detection of a 10 point drop 61.2% against 72.9%, v0.2 against v0.1), so the current rule is one smooth rule, not a better one at every size. The 4% at 200 cases holds only if the target does not crash (a 1% crash rate doubles it). And the committed baseline is one noisy draw: the chance that it leaves more than 15% of later unchanged pull requests blocked is 28.8%, 14.0% and 7.2% at 45, 100 and 200 cases. `evalsprint noise RUN` prices the whole gate (the pass-rate rule and the critical-case rule together) for the repeat protocol of a run, from the flip rate of its repeated cases, and prints "about" figures: it assumes that the noise measured on the repeated cases is the noise of every case, and it needs at least 20 repeated cases (with fewer it prints "not estimated" and no rate, which is what the 10 cases of the `evalsprint init` scaffold give: repeat every case of a suite of 20 or more cases with `run --repeat 3`, or use the tables).

**Two more measured sentences, for a suite with critical cases and for a target that crashes** (exact, at 5% noise per attempt; `scripts/gate_numbers.py`). With 8 critical cases in a 45-case suite, an unchanged change is blocked 36.67% of the time with one attempt per case, 5.79% with every case repeated 3 times, and 1.11% with every case 3 times and the critical ones 5 times (`repeat: {n: 3, per_tag: {safety: 5}}`); repeating every case 5 times alone gives 0.92% and costs more. A target that crashes on 5% of the calls makes an unchanged 100-case change blocked in 54% of the runs (38% of all runs are unhealthy and never compared); one retry inside the run (`target_retries: 1`, the default) brings it to 8%. The same retry also hides a candidate that starts to crash on some calls: with `target_retries: 1` and 100 cases, one whose target crashes on 10% of its calls is blocked in 11% of the runs and one that crashes on 20% of its calls in 39%, against 7% for an unchanged candidate. The gate now blocks a change of `target_retries`, prints the retries of both runs and warns when the candidate retried at least 10 percentage points more of its calls than the baseline, but that warning is weak for small increases (against a baseline that retried 5% of its calls it fires in 11 of 100 comparisons for a candidate that crashes on 10% of its calls and in 89 of 100 for 20%), so the crash and retry counts of the report must still be read next to the gate.

## 3. Repeats and the noise floor

`repeat: {n: 3, per_tag: {safety: 5}}` runs every case 3 times and the cases tagged `safety` 5 times: a case runs the largest `per_tag` count among its tags, else `n` (`run --repeat N` sets `n` and keeps `per_tag`; the older `{n: 5, tags: [safety]}` is read as `{n: 1, per_tag: {safety: 5}}`, and `summary.repeat` always records `{"n", "per_tag"}`). The case outcome is the **majority** of the attempts (errors at or above half of them make it an `error`; a tie is a `fail`, the conservative side). `stability` is the share of attempts that agree with the majority and `summary.stability.flip_rate` is the share of repeated cases whose attempts disagree: a direct measurement of your noise, which is otherwise an assumption. **Repeat below 150 cases.** The second reason to repeat is a small test set: with one attempt per case, 45 cases cannot tell noise from a regression well. Taking the majority of three attempts of **every** case (`repeat: {n: 3}`, which the shipped template enables) cuts the flip probability of a case from 5% to 0.725% (3p^2(1-p) + p^3), so at 45 cases the false-alarm rate falls from 10.6% to 0.3% and the detection of a 10 p.p. drop rises from 66.6% to 81.6%, and at 100 cases they go from 7.1% to 0.3% and from 79.7% to 97.5% (exact, `scripts/gate_numbers.py`), at three times the target and judge calls. This assumes the attempts are independent: noise that is the same on every attempt of a case, such as a judge that is always wrong on it, is not reduced by repeating, so these are best-case figures. At 30 cases it still cuts false alarms (6.5% to 0.1%) but lowers the detection of a 5 p.p. drop (27.1% to 20.8%): the 3-case floor stays, and a test set that small is too small for any gate. From 150 cases on the block can go if the target does not crash (a crash is not noise that a single attempt's majority removes: see section 2). The `repeat` protocol is part of the baseline: a change to it is a regression reason. **Critical tags** are the first reason to repeat, because one pass-to-fail flip blocks the change. For 8 critical cases and 5% noise per attempt, an unchanged system is blocked 32% of the time with one attempt, 5.6% with a majority of three and **0.92%** with a majority of five, while a case that really broke and fails 80% of its attempts is caught 80%, 89.6% and **94%** of the time. Unanimity of three (fail only if all three fail) was rejected: 0.10% false alarms but only 51% detection. Five attempts cost five times as much for those cases; `compare` warns when critical cases ran fewer than five times, and the warning recommends `per_tag: {<critical tag>: 5}` added to the existing block, never a single block that replaces the protocol. The numbers are closed-form (independent attempts) and `tests/test_templates.py` recomputes them. **Repeat the critical cases and only those.** `n: 3` on every case leaves the critical rule at 5.6%, and `n: 5` on every case pays five times for the whole suite: the total false alarm of the gate (pass-rate rule or critical rule) at 45 cases with 8 critical ones and 5% noise is **5.79%** with `repeat: {n: 3}`, **1.11%** with `repeat: {n: 3, per_tag: {<critical tag>: 5}}`, 0.92% with `repeat: {n: 5}`, 9.37% with the critical cases at 5 attempts and the rest at 1, and 36.67% with no repeats at all (the critical rule alone is 32%). These are exact: the two rules share the critical cases (a critical case that flips to fail also counts in the pass-rate rule), so they are computed over the joint distribution of the paired counts, not as the product of two independent rules, which overstates them (slightly with repeats, by about 3 points with none). The protocol recommended everywhere in these docs is therefore `repeat: {n: 3, per_tag: {<critical tag>: 5}}` below about 150 cases, and `per_tag` alone from 150 cases on.

## 4. Calibration: is the judge right?

Experts label a sample blind (the judge's verdict is hidden, and even the stratum recorded in the label file is an opaque keyed token, an HMAC with a per-run secret that stays in the run folder, so it cannot leak it). The sample is **stratified** by the judge's verdict so failures are not drowned by passes, which biases naive rates; `calibrate` therefore weights each label by **Horvitz-Thompson weights N_h / n_h** (stratum size over labeled count), using the strata recorded in the labeling file. The weighted true-positive and true-negative rates are then used in the **Rogan-Gladen** correction of the run's pass rate, `(observed + TNR - 1) / (TPR + TNR - 1)`, which refuses to correct a judge that is no better than chance. Cohen's kappa gets a bootstrap interval, and the **decision is taken on the interval of the weighted kappa, not on a point estimate and not on the raw sample's kappa**. The raw sample is stratified on the judge's own verdict, so its kappa flatters a lenient judge; the weighted kappa is the whole run's (Horvitz-Thompson weights again). Deciding on the sample's kappa released judges of true kappa around 0.6 in 12 to 53% of simulated replications where 7% was documented; on the weighted interval the same judges are released in at most 3.0% (2.2% at 40 labels). Lower bound >= 0.6 is `usable`, but only with at least **40 labeled cases** (the smallest number that keeps the release rate of a judge of true kappa about 0.6 under 10% in every profile the critic tried; the plain weighted bootstrap would have needed 60); lower bound >= 0.8 is `trustworthy` only when `tnr_reliable` also holds; upper bound < 0.6 is `not_trustworthy`; fewer than 30 labels is `insufficient_data`; everything else is `inconclusive`. `tnr_reliable` is a **screening flag, not a guarantee**: it says the true-negative rate (how many bad outputs the judge catches) looks measured precisely enough: at least 10 human fails, a TNR of at least 0.75 and a 95% interval no wider than +/-0.175, where the interval is a closed-form Wilson interval at the delta-method effective n of the weighted TNR. It is **monotone in judge quality**: a judge with fewer misses is never less reliable, so a perfect judge is certified once it has enough human fails (version 0.1 demanded at least 5 bad outputs the judge let through, so no perfect judge could ever be `trustworthy`). When the flag is true, the interval covered the run's true TNR in 99.8% of 10,327 simulated replications (the first design tried, a Wilson interval at a Kish effective n, covered 81 to 88%, below the 90% required, and was rejected). The flag is still a threshold on an estimate, so it also selects lucky reads: a judge whose true TNR is 70% passes it in 2% to 28% of simulated runs, depending on the design, and it does not show that the true rate is at least 0.75. When few labels disagree, a plain bootstrap would say "certain" (with nobody disagreeing every resample is identical), so the interval is smoothed with Jeffreys pseudo-counts (0.5 per confusion cell the run allows). It falls smoothly as disagreements are added and converges to the plain bootstrap as labels grow. This replaced an earlier Wilson floor that applied only up to two disagreements and made three easier to release than two. With perfect agreement and every case labeled, the judge is first released (`usable`) at 40 labels (45 when 90% of the human labels are pass), the weighted lower bound first reaches 0.8 at 32, 39, 53 and 96 labels at a human pass rate of 50%, 70%, 80% and 90%, and it is `trustworthy` from 40, 41, 53 and 96 labels when exactly that share of the labels is pass (`tnr_reliable` first holds at 30, 32, 48 and 96): `python3 orchestration/2026-09-29_kit-v0.2/cycle3/mlops-engineer/perfect_agreement_scan.py` runs the real `calibrate` on every label count. The price is power: a judge with true kappa 0.82 is released 18% of the time at 40 labels and 74% at 100, and at 100 labels a judge whose true TNR is 0.7, 0.8, 0.9, 0.95 or 1.0 is called reliable in 2%, 15%, 52%, 81% or 98% of the samples (26%, 68%, 98% and 100% at 150 labels; never at 40 or 60). Plan about **150 labels** for the calibration of a judge that gates merges, and budget by how often the humans pass the output: the decision needs human fails, so the best case (a judge that agrees with every label) needs 40, 48, 67 and 124 labels when every case is labeled at a human pass rate of 50%, 70%, 80% and 90% (the number of human fails in a run is random and fewer fails need more labels, so each figure is the smallest number for which at least 80% of the runs get there; the 41, 53 and 96 above are for exactly that share of passes), 40 to 130 labels when a stratified sample of a run of 200 or 400 cases is labeled, and more for a judge with errors (a judge that is right 95% of the time on both kinds of verdict is not reliably `trustworthy` within 150 labels of a 200-case run at a 70%, 80% or 90% human pass rate). The full table is `calibration.labels_budget_table()` and is printed in `docs/SPRINT_PLAYBOOK.md`; the simulations (real `labeling.select_sample` and `calibrate`, fixed seeds) are in `orchestration/2026-09-29_kit-v0.2/cycle4/loopback1/eval-scientist-judge/`. Expect `inconclusive` more often than a verdict. Labels that are all judge-pass (or all judge-fail) make the kappa degenerate: `calibrate` then says to label the cases the judge failed, and never to revise the rubric. When the next round of rubric examples comes from these labels, `calibrate --export-fewshot` sets a random holdout of the labeled cases aside and `--exclude-holdout` leaves them out of the next calibration, so the judge is not graded on cases it was shown. After a change to the judge or the prompt, label only the cases that have no label for their current output: the labeling export takes the earlier label files (`previous_labels`) and leaves out every case whose current output already has a usable label, and `calibrate` reads several label files as one. Those cases are only the changed outputs when the earlier labels covered every unchanged case (a full earlier pass); after a sampled pass the export also draws unchanged cases that never had a label, because the new labels have to stand for every case without a carried label. Labeling only the changed outputs after a sampled pass biases the true-negative rate (the independent review of cycle 4 measured 6 to 7 points); through the tool's own export the carried-over estimate is unbiased. A calibration records the `judges_sha` it was made for; when the run's judges differ, the report and the comparison warn that it describes a different judge configuration. `labels_needed_estimate` says how many labels would narrow the interval to +/-0.10, never more than the number of cases the run has to label (it then says to label them all and add cases or repeats). The gate reads the same weighted interval: with `require_calibration: true`, the calibration rule fails when the decision is not `usable` or `trustworthy` (so `inconclusive`, `not_trustworthy` and `insufficient_data` fail) or when the weighted lower bound is below `min_judge_kappa`; without `require_calibration` these are warnings. Reading the sample's kappa there would have let a lenient judge through the gate that the calibration itself would not release (the sample lower bound cleared 0.6 for a judge of true kappa below 0.6 in 24 to 41% of simulated replications, the weighted one in 2 to 3%). A `calibration.json` from an older evalsprint has no weighted kappa; the gate then falls back to the unweighted one, labels it `legacy` and warns, so re-run `calibrate` with the current version.

## 5. Judge hardening

The output under test is untrusted text that the judge reads. The judge prompt wraps input, reference, context, output and few-shot examples in delimiters that carry a **per-call random nonce** (delimiter names inside the content are neutralised), states that everything inside is data to grade and never instructions, puts the trusted grading instruction **after** the data, shows the response shape as `true|false` rather than a pre-filled `true`, and breaks even-sample ties toward `fail`. The trusted block carries the same nonce in its header, and imitations of that header found inside the content are neutralised, so the real one is the only one. An output longer than `max_output_chars` (default 20,000) is not sent to the judge at all: the case fails at zero cost, because a huge output buries the criteria and costs real money; every other untrusted section is cut at `max_section_chars`. `details.injection_suspected` flags outputs that contain delimiter-like tags or phrases such as "ignore all previous instructions". It is a hint for a human, not a detector: the independent review of evalsprint 0.1 measured a recall of 43% on injection attempts and 27.5% false positives on legitimate text (the heuristic is unchanged in 0.2 and was not measured again). The hardening shrinks the attack surface that the cycle-1 review found wide open; it is not a guarantee.

## 6. What is and is not claimed

Claimed: the statistics in `stats.py` match independent implementations (exact binomial McNemar, Wilson, kappa, Rogan-Gladen, 27 of 27 checks); a stratified sample re-weighted by its strata recovers the true pass rate (simulated bias under 0.3 p.p. at 40 labels); the gate's false-alarm and detection rates in section 2 (an exact enumeration, recomputed by the test suite); the CI workflows behave as described when run step by step with stubs, including against the injection of a newline into the exit code that the pre-fix workflow let through.

**Not claimed**, and to be said out loud to clients:

- **"The gate never gives a false alarm."** With one attempt per case it gives about 1 in 9 at 45 cases, 7 in 100 at 100 cases and 4 in 100 from 150 cases on, at the assumed noise (0.3 in 100 at 45 cases when every case is repeated 3 times, if the attempts are independent). The noise levels (2, 5, 10%) are an assumption; `flip_rate` measures yours.
- **"The false alarm never exceeds 11%."** It peaks at 12.3% at 54 cases with 5% noise, and at 15.1% with 10% noise.
- **"v0.2 is better than v0.1 at every size."** Between 60 and 149 cases the rule of v0.1 had a lower false alarm and a higher detection of a 10 p.p. drop at 84 of 90 sizes at 5% noise (at 10% noise v0.2 is the stricter rule and blocks less often). v0.2 removes the cliff at 150; that is what it claims.
- **A false-alarm rate for one pull request.** The committed baseline is one noisy draw: the chance that it makes more than 15% of later unchanged pull requests fail is 28.8%, 14.0% and 7.2% at 45, 100 and 200 cases.
- **"At most 5% from 150 cases on" for a target that crashes.** A 1% crash rate doubles it at 200 cases (4.0% to 8.0%).
- **"The judge resists prompt injection."** The hardening is structural and unit-tested; behavior against real models under attack was **not tested** (no API budget). `injection_suspected` finds 43% of the attempts and flags 27.5% of legitimate text (measured on 0.1). Neither were position, verbosity or self-preference bias.
- **A cheap way to be sure about crashes.** Counting a crash as a failure removes a way to hide regressions and adds false alarms when the target crashes for reasons that have nothing to do with the change.
- **"`evalsprint noise` gives your suite's false-alarm rate", or "its figure is a pessimistic bound".** It prices the whole gate (the pass-rate rule, the critical-case rule and the two together) for the repeat protocol of the run it reads, exactly for a model and "about" for your suite: independent cases and attempts, the noise measured on the repeated cases taken as the noise of every case, a true drop spread over every case. It needs at least 20 repeated cases (below that it prints "not estimated", as it does for the 10 cases of the scaffold) and it prices a flip rate of 0 at the upper 95% bound, not at zero. For the protocol the docs recommend (`n: 3`, `per_tag: {safety: 5}`), 45 cases, 8 critical cases and 5% noise per attempt, it prints 0.21% for the pass-rate rule, 0.92% for the critical-case rule and 1.11% for the whole gate (the command estimates the noise from a count of flips, so a real run gives figures close to these, not these). Hand its output over with the measured flip rate and the assumption.
- **"`target_retries` makes crashes harmless", or "the gate shows crashes".** A retry hides a transient crash from the pass rate and from the error rate. The gate blocks a changed `target_retries` (`allow_target_retries_change`), prints the retries of both runs in `gate.md` and `gate.json` (the report shows them too) and warns when the candidate retried at least `retry_share_warn` (10 percentage points) more of its calls than the baseline, but that warning is weak for small increases: against a baseline that retried 5% of its calls it fires in 0.12% of the comparisons of an unchanged target at 100 calls, in 11.2% when the candidate's calls crash 10% of the time, in 88.8% at 20% and always at 50% (exact, calls that crash independently, `target_retries: 1`). With that retry a target that crashes on 10% of its calls is blocked in 11% of the runs and on 20% in 39% (an unchanged one, 7%). A crash on a fixed 10% of the cases is blocked at any retries value, because the run is unhealthy.
- **"After a change, only the outputs that changed need a label."** True only when the earlier labels covered every unchanged case. The export draws from every case without a usable label (the changed outputs and the never-labeled unchanged ones); if the humans label only the changed outputs after a sampled pass, the true-negative rate is biased by about 6 to 7 points (300 cases, 20, 40 or 80 new labels). Through the tool's own export the carried-over estimate is unbiased, and less precise than pooling the labels when the outputs are exchangeable.
- **"A perfect judge is certified with 40 labels", or a label budget that ignores the human pass rate.** With perfect agreement the judge is released (`usable`) at 40 labels (45 when 90% of the human labels are pass); it is `trustworthy` first at 40, 41, 53 and 96 labels at 50%, 70%, 80% and 90% human pass when exactly that share of the labels is pass, and, because the number of human fails in a real run is random, in at least 80% of the runs only from 40, 48, 67 and 124 labels (`labels_budget_table`, the table of the sprint playbook). Those are floors for a perfect judge; a judge with errors needs more, so plan about 150.
- **The whole-gate figures as an independence approximation.** The false alarm of the whole gate (pass-rate rule or critical rule) is the exact joint probability over the paired counts and the critical flips, not the sum of two independent rules: 36.67% (no repeats), 5.79% (`n: 3`), 1.11% (`n: 3`, critical 5) and 9.37% (critical 5, the rest 1) for 8 critical cases in 45 (`scripts/gate_numbers.py`, `whole_gate_false_alarm`). The independence approximation (`total_false_alarm`) stays in the script only to show the difference, and no doc quotes it.
- **That the tag-drop warning covers small tags.** A non-critical tag with fewer than `tag_drop_min_cases` (20) paired cases never warns: with 10 as the minimum, 10 tags of 10 cases with no change raised a spurious warning in 43.4% of the comparisons at 5% noise, and with 20 it is 0%. Even at 20, five tags of 20 cases raise a spurious warning in 3.3% of the unchanged comparisons at 5% noise and in 14.8% at 10%. It is a warning, never a reason.
- **A precise true-negative rate with about 40 labels, or `tnr_reliable` as a guarantee of TNR >= 0.75.** `tnr_reliable` is never true at 40 or 60 labels and rarely at 100 for a judge that is not near perfect: it is a screen that tells you when the TNR looks measured, it does not measure it sooner, and a judge whose true TNR is 70% still passes it in 2% to 28% of simulated runs. The earlier bootstrap interval for the TNR covered the truth only 52 to 68% of the time at 40 labels.
- **That the corrected pass rate describes this exact test set.** Its interval targets the population the test set was sampled from.
- **That calibration simulations match reality.** They assume independent judge errors; real judge errors cluster on hard cases, so the intervals are probably optimistic.
- **Real-model results from the demo.** The bundled demo runs on a seeded simulator and says so everywhere; its numbers show that the pipeline works, not how any model performs.
- **That the candidate results are genuine.** The CI compares in a job that never runs the pull request's code, with the gate settings, the baseline and the kit of the base branch, so the PR cannot loosen its own gate or patch the code that judges it. The candidate results themselves are still produced by the PR's code: a change whose adapter returns canned good answers, whose judge always passes or that writes its own result file passes the comparison. Code review catches that, which is why CODEOWNERS is part of the setup.
- **That the job that runs the pull request's code cannot read your kit's token.** It can, while it installs the requirements of the pull request (a requirement or a build script is code from the PR). Keep the token read-only and limited to the kit repository, or vendor the wheel of the kit and give that job no token.
- **That the gate covers everything a pull request can touch.** It does not see the code of the target or what a `custom` judge imports, the *coverage* of the test set (only edits and removals), the kit pin in `evals/requirements.txt` (the comparison uses the base branch's pin and only warns about a different version) or the workflow files. Those are protected by code-owner review, not by a statistic.
- **That a baseline taken from a partial run is a baseline of the suite.** `evalsprint baseline` warns, without refusing, when the run was limited (`--limit`, `--tags` or ids: `summary.selection.limited`) or does not record its selection: against a full candidate run only the cases of the baseline are paired, every other case is a new case in every comparison, and the gate decides on the cases it has.
- **Verified CI on a real runner.** Workflows were run by an emulator of GitHub Actions with stub programs, not on GitHub-hosted runners, and `gh` was not run for real. Windows guidance is from reading the code and simulating encodings, not from a Windows machine.
