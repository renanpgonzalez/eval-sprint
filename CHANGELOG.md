# Changelog

What changed in each release of the Eval Sprint kit, and what to do when you upgrade. Versions are the git tags of the kit repository (`evalsprint @ git+https://github.com/renanpgonzalez/eval-sprint@vX.Y.Z` in a client's `evals/requirements.txt`). The interfaces are in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), what the numbers mean in [docs/METHODOLOGY.md](docs/METHODOLOGY.md).

## [0.2.0] - 2026-09-30

Prepared on branch `ciclo3-wip`; the tag `v0.2.0` is created after the merge into `main`.

### Upgrading from v0.1 to v0.2

Do this in **one reviewed pull request** per client repository: bump the pin in `evals/requirements.txt` to `@v0.2.0`, refresh the baseline (`evalsprint baseline`, or the *Update eval baseline* workflow) and merge both together. A baseline written by v0.1 blocks the pull request that bumps the pin only in two cases (items 2 and 3): the suite has a custom judge (`judges_sha` now hashes the judge's code) or the candidate's `repeat` differs from the baseline's (the new template ships `repeat: {n: 3}`). Otherwise the comparison passes with the kit-version warning of item 4 and a warning that the baseline does not record `target_retries` (item 8), or fails if you set `require_same_kit_version: true`. Refreshing the baseline in the same pull request is still how you bring it to the protocol you will run from now on (checked against the real v0.1.0 kit).

1. **The `auto` gate rule is new.** v0.1 had two modes that switched at 150 paired cases (`auto-small`, `auto-large`), and the detection of a 10 point drop fell from 88.3% to 81.4% at the switch. v0.2 has one rule for every size: the net loss (pass to fail minus fail to pass) must be at least `max(3, ceil(n / 50))` cases **and** a one-sided exact McNemar test must give `p < alpha(n) = 0.0575 + 0.1925 / (1 + (n / 85)^4.5)`. Comparison files written by v0.1 (`gate_mode: "auto-small"` or `"auto-large"`) still render and are read as `auto`. **It is not better at every size**: between 60 and 149 cases the v0.1 rule had a lower false alarm and a higher detection of a 10 point drop at 84 of the 90 sizes at 5% noise (every size but 60 to 62 and 78 to 80; at 10% noise v0.2 is the stricter rule and blocks less often), and the new false alarm peaks at 12.3% at 54 cases (15.1% at 10% noise). See the numbers in the workflow README, section 9.
2. **`judges_sha` now covers the source of custom judges.** Until v0.1 the code of a `custom` judge was not part of the fingerprint; v0.2 hashes the file the judge's `callable` points at (and, since v0.2.0, every file in its `data_files`). A baseline written by v0.1 for a suite **with a custom judge** has a different `judges_sha` than the same suite run by v0.2, so `compare` ends as a regression: "judge configuration or rubric changed: update the baseline in a reviewed PR (judges_sha 68662b5d470b -> b912c8f9fcfa)", followed, when the baseline was recorded by evalsprint 0.1, by a note that v0.2 also hashes custom-judge code and `data_files`. Refresh that baseline in a reviewed PR. A suite with no custom judge keeps its `judges_sha`, and a v0.1 baseline compared by v0.2 passes with the kit-version warning of item 4 (both checked with the two real versions). Rolling the pin back to v0.1 is blocked the same way, in reverse.
3. **`summary.repeat` is always written**, as `{"n", "per_tag"}`. A v0.1 summary has `judges_sha` but no `repeat` and is read as "every case ran once", so a candidate run with the new template's `repeat: {n: 3}` is an evaluation-protocol change (`allow_repeat_change: false`: a regression reason) until the baseline is refreshed with the same protocol. The old spelling `{n: 5, tags: [safety]}` still works and means `{n: 1, per_tag: {safety: 5}}`.
4. **A different kit version is a warning**, patch included ("evalsprint version differs between baseline and candidate"), or a reason with `require_same_kit_version: true`. It is one more warning on the pull request that bumps the pin, not a failure by default.
5. **Replace the v0.1 workflows.** The v0.1 `evals.yml` (jobs `check-secrets`, `changes`, `evals`, `comment`, `gate`) runs the pull request's code and the comparison in the same `evals` job, and three attacks from the adapter (rewriting the trusted gate and baseline, patching the installed `evalsprint`, swapping the kit in `requirements.txt`) turn a real regression into a pass against it (`tests/fixtures/ci/evals_single_job.yml`, run by `TamperTests`). Write the new ones on a branch with `evalsprint init --ci --force`, review the diff against your copies (re-apply your `EDIT` lines: `EVAL_PATHS`, secrets, timeout) and merge it with code-owner review. Copy `CODEOWNERS.example` to `.github/CODEOWNERS`, require the check **LLM evals gate**, and set `REQUIRE_BASELINE: "true"` once the baseline is merged.
6. **The read token of a private kit (`EVALSPRINT_READ_TOKEN`) is visible to the job that runs the pull request's code** while it installs the requirements (see "Changed" below). If the kit must stay private from whoever can open a pull request, vendor the wheel (workflow README, section 2).
7. **Smaller things.** `tag_drop_min_cases` defaults to 20 (an explicit value in your `gate:` is kept). The scaffold's `eval.yaml` ships `repeat: {n: 3}`; add `per_tag: {<critical tag>: 5}` for your critical cases instead of `n: 5` on every case. `runs/` and `.label_secret` belong in `.gitignore` (`evalsprint init` writes them). The templates moved from the repository's `templates/` folder to `evalsprint/templates/` inside the package, so `evalsprint init` works from a plain `pip install` and there is no checkout to copy from.
8. **`summary.target_retries` and `summary.selection` are new.** A v0.1 baseline has neither. `compare` warns that the baseline does not record `target_retries` (a change of the retry setting, which hides transient crashes, cannot be detected) and `target_retries_changed` is `null`; refreshing the baseline with v0.2 makes both sides comparable, and from then on a changed `target_retries` blocks (`allow_target_retries_change: true` makes it a warning). `evalsprint baseline` warns, without refusing, when the run it copies was limited (`--limit`, `--tags`, ids) or does not record `selection`, so build the baseline from a run of the whole suite.

### Added

- **Gate.** One monotone `auto` rule (above), with `gate_mode`, `effective_min_net_loss` and `effective_alpha` in the comparison. Attempt-level errors: `n_attempts`, `attempt_error_rate`, `flaky_crashes` and `max_error_rate` checked per attempt, so a crashed attempt cannot hide behind a majority that passed. The evaluation protocol is part of the baseline (`allow_repeat_change`), and so are `target_retries` (`allow_target_retries_change`; `retry_share_warn` warns when the candidate retried 10 percentage points more of its calls than the baseline; the warning is weak for small increases: 0.12% false warnings at 100 calls against a baseline that retried 5% of its calls, and 11.2% for a candidate whose calls crash 10% of the time, 88.8% at 20% and always at 50%) and a custom judge's source (`allow_judge_changes`). A warning when a non-critical tag fell by 20 points (`tag_drop_warning_pp`, `tag_drop_min_cases`). `compare.expected_gate_rates(n, noise)` computes the exact false alarm, detection and baseline-lottery rates of the gate in force with one attempt per case, and `compare.expected_gate_rates_protocol(attempts, critical, noise)` those of the whole gate (pass-rate rule and critical-case rule, exact over their joint distribution) for the attempts of every case. The comparison carries `target_retries_changed` and `target_retries` (`baseline`, `candidate`, `changed`; `configured`, `retried_calls`, `attempts`, `share` per side), and `gate.md` prints one line with the retries of both runs whenever either retried or the value differs.
- **`repeat.per_tag`.** `repeat: {n: 3, per_tag: {safety: 5}}`: a case runs as many times as the largest count among its tags, else `n`. At 45 cases with 8 critical ones and 5% noise the total false alarm (pass-rate rule and critical rule together, exact) is 1.11% with `{n: 3, per_tag: {<critical>: 5}}`, 5.79% with `{n: 3}` alone and 0.92% with `n: 5` on every case (at five times the cost). `compare` recommends the `per_tag` line. `run --repeat N` sets `n` and keeps `per_tag`.
- **An inert PR comment.** Every value of `gate.md` that comes from a run artifact (case ids, tags, run ids, kit versions, `judges_sha`, the judge's name and its calibration decision) is printed in a code span with URLs, mentions, issue references and HTML entities made inert, so a hostile value in a pull request's own `summary.json` cannot notify anyone or plant a link (the engineering review's hostile payloads, extended to 48 values on 29 surfaces, 1392 cells: 0 findings, against 103 before the fix). `gate.json` and the CLI keep the plain text.
- **Runner.** `run --resume DIR [--retry-errors]` continues an interrupted run from `results.partial.jsonl` without paying again for finished attempts. The fingerprint it checks is the judges, the target (callable, `params` and `target.source_sha`, a hash of the **one file** the callable lives in: edits in the modules that file imports are not detected) and the repeat protocol; when it differs nothing is reused and `summary.resumed_from.fingerprint_mismatch` names the part (`judges_sha`, `target`, `target_source`, `repeat`). `--retry-errors` also re-runs the crashed attempts of repeated cases that otherwise finished (`resumed_from.retried_errors` counts attempts). Ctrl-C (exit 130) and `SIGTERM` (exit **143**, new) drain, keep the partial file and print the resume command. A resume takes `.resume.lock` in the run folder, which exists only while it runs: a second concurrent resume exits 2, and a file left by `kill -9` is harmless. `target_retries` (default 1, at most 5, 0 switches it off) calls a target that crashed again inside the run; retries are paid, counted in the cost and in `n_target_retries`, and **a target that is not idempotent needs `target_retries: 0`**. `summary.placeholder` is true when the target callable is a function named `offline_stub` or any LLM judge has the provider `mock` (after `${VAR}` and `--set` expansion): `baseline` refuses such a run without `--force`, the report shows a banner and `compare` warns when the baseline is one. `n_oversize` counts outputs too long to send to the judge. `summary.target_retries` records the configured value and `summary.selection` says whether the run covers fewer cases than the configuration selects (`limited`, `n_selected`, `n_config`, `limit`, `tags`, `ids`). `repeat.per_tag` below `n` is honoured, and `tags` together with `per_tag` is a configuration error.
- **CLI.** `evalsprint init [--ci] [--force]` (scaffolds `evals/`, the workflows and `.gitignore`; never overwrites without `--force`), `evalsprint history`, `evalsprint noise RUN [--gate PATH | -c eval.yaml]` (prices the whole gate, the pass-rate rule and the critical-case rule together, for the repeat protocol the run used, from the flip rate of its repeated cases: "about" figures for the false alarm, the detection of a 5 and a 10 point drop and the baseline-lottery tail. It needs at least 20 repeated cases and prints "not estimated" with the fix below that, which is what the 10 cases of the `init` scaffold give; it prices a flip rate of 0 at the upper 95% bound, assumes that the noise measured on the repeated cases is the noise of every case, and prices an even number of attempts exactly, a tie counting as a fail, while 3 or 5 stay the recommendation), `calibrate --export-fewshot` / `--exclude-holdout`, repeatable `calibrate --labels`, `label --previous-labels` (skip the cases whose current output already has a label: only the changed outputs need a label when the earlier labels covered every unchanged case (a full earlier pass); after a sampled pass the export also draws unchanged cases that never had a label).
- **Judge and calibration.** Size caps for judge input (`max_output_chars`, `max_section_chars`: a huge output fails without a call), a nonce in the trusted header, a keyed (HMAC) stratum token with a per-run secret so blind labels stay blind, the decision on the interval of the weighted kappa with a smoothed bootstrap for few disagreements, `tnr_reliable` monotone in judge quality (a perfect judge can be `trustworthy`), a stale-calibration warning (the `judges_sha` in `calibration.json` differs from the run's), and `calibration.labels_budget_table()`: the labels a judge needs by the share of outputs the humans pass (40, 48, 67 and 124 labels for a judge that agrees with every label when every case is labeled at 50%, 70%, 80% and 90% human pass rate, for at least 80% of the runs: the number of human fails in a run is random and fewer fails need more labels).
- **CI templates.** The job split: the pull request's code runs in one job (`evals`), the comparison in another (`compare`) that uses only the gate settings, baseline and kit pin of the base branch, read by a `trusted` job at one base commit; the `gate` job also fails closed when `check-secrets`, `changes` or `trusted` did not succeed.
- **Docs.** The gate paragraph (the independent review's own client paragraph, word for word, with a second paragraph for what it leaves out and a third with two measured sentences on critical cases and on crashes), the false-alarm and detection tables, the whole-gate figures for critical tags (exact: the pass-rate rule and the critical rule share the critical cases, so they are computed over their joint distribution), the 84-of-90 comparison with v0.1 stated at 5% noise and its 10% noise side, every decimal percentage of the client docs scanned against a recomputation by the test suite, the labels budget, the playbook.

### Changed

- **Everything that crosses from the job that runs the pull request's code to a trusted job is validated (release blocker).** The exit code of the suite is a job output, so the pull request's code decides every byte of it: a newline in it could close its own heredoc in `$GITHUB_OUTPUT` and write `verdict=pass`, and the gate turned green on a real regression (findings H2 and H4 of the independent review). Now the exit code must be 1 to 3 digits or it counts as 255 (`case "$RUN_CODE" in ''|*[!0-9]*|????*) RUN_CODE=255;; esac`), only validated values are written to `$GITHUB_OUTPUT`, the verdict is one of a closed set, the `gate` job validates the code it receives, and only listed files are taken from the artifact, as regular files that are not symlinks. `tests/test_templates.py` replays the attack against the pre-fix workflow (green: the test proves the attack is live) and the shipped one (blocked), and removing any one of the three checks makes the tests fail. A genuine exit code `0` with forged candidate files is still not caught: review is the control.
- **Artifacts are explicit file lists**, never folders (`results.jsonl`, `summary.json`, `calibration.json` when present, `report.html`, `gate.md`, `gate.json`), with `ARTIFACT_RETENTION_DAYS` (14) as the retention of the run artifacts.
- **Honest wording about `EVALSPRINT_READ_TOKEN`.** The token IS present (in the environment of the install step and in git's config) while the job that runs the pull request's code installs the requirements, and a requirement or a build script is code from the pull request. The earlier wording said it was removed before the suite starts and left the impression that the pull request's code could not see it. The token should be fine-grained, read-only and limited to the kit repository; for a kit that must stay private, vendor the wheel in `evals/vendor/` and give that job no token.
- **`evals-baseline.yml`** refuses a placeholder run and shows the attempt error rate in the pull request body.
- **`evalsprint baseline` warns, without refusing, about a run over part of the suite** (`--limit`, `--tags`, ids: `summary.selection.limited`) and about a run that does not record `selection`: a candidate of the whole suite meets such a baseline on only those cases, and every other case is a new case in every comparison.
- **A `summary.json` with text where a number belongs** makes `report`, `compare` and `baseline` stop with a one-line error that names the field (`the field 'pass_rate' should be a number but is ...`) and the exit code the command already used, instead of a Python traceback.
- **`label --previous-labels` says when only the changed outputs need a label**: when the earlier labels covered every unchanged case; otherwise the export also draws the unchanged cases that never had a label.
- **`tag_drop_min_cases`** 10 to 20 (with 10 tags of 10 cases and 5% noise a no-change comparison raised a spurious warning 43% of the time).
- **Templates are package data** (`evalsprint/templates/`, read through `importlib.resources`): `init` works from a plain `pip install`.
- **Claims removed from the docs, because the review measured otherwise.** "False alarm never above 11%" (peak 12.3% at 54 cases, 15.1% at 10% noise); "v0.2 is better than v0.1 at every size" (v0.1 was better at 84 of 90 sizes from 60 to 149 cases at 5% noise; at 10% noise v0.2 is the stricter rule); a false-alarm promise for a single pull request (the committed baseline is one noisy draw: the chance that it leaves more than 15% of later unchanged pull requests blocked is 28.8%, 14.0% and 7.2% at 45, 100 and 200 cases); "at most 5% false alarms from 150 cases on" for a target that crashes (a 1% crash rate doubles it at 200 cases); a perfect judge certified with 40 labels without saying that depends on how often the humans pass the output; `tnr_reliable` as a guarantee (it is a screening flag); `n: 5` on every case to protect critical tags (use `per_tag`).

### Known limits

The candidate results come from the pull request's own code, so a change that fakes them passes; the code of the target and what a custom judge imports are not hashed (`--resume` hashes the target's one source file, not the modules it imports); `injection_suspected` is a hint (43% recall and 27.5% false positives as measured on v0.1, not measured again); the CI was run by an emulator, not on a GitHub-hosted runner; the Windows guidance was not run on Windows; nothing was measured with a real model (no API key was available). New in this release: `evalsprint noise` is a model of the suite (at least 20 repeated cases, one noise for every case, independent cases and attempts), not a measurement of its false alarm; `retry_share_warn` is a weak warning for small increases of the retried share, and a retry hides a transient crash from the pass rate; the tag-drop warning never covers a tag of fewer than 20 paired cases, and five tags of 20 cases still raise a spurious warning in 3.3% of unchanged comparisons at 5% noise (14.8% at 10%).

## [0.1.0] - 2026-09-29

The first release: the kit behind the fixed-price Eval Sprint service.

- **Test set.** JSONL cases (id, input, reference, expected behavior, tags, per-case checks) with validation and statistics (`evalsprint describe`); `case_sha` over every field but the id.
- **Runner.** `evalsprint run` with a pluggable target (`fn(input, params)`), deterministic judges (`contains`, `not_contains`, `regex`, `max_chars`, `min_chars`, `json_valid`, `exact_match`, `custom`, per-case `checks`) and an LLM judge with binary rubric criteria, critical criteria, `samples` self-consistency, nonce-delimited untrusted sections and a trusted instruction after the data; `repeat` with a majority vote; outcome `pass`, `fail` or `error` (errors kept out of pass rates; an unhealthy run exits 3); cost from real token usage; atomic writes.
- **Calibration.** A blind single-file HTML labeling tool, `evalsprint calibrate`: agreement, Cohen's kappa with a bootstrap interval, the decision taken on that interval, true-positive and true-negative rates re-weighted for the stratified sample (Horvitz-Thompson), Rogan-Gladen corrected pass rate, every disagreement.
- **Report.** One self-contained HTML file: pass rate with Wilson intervals, by tag and judge, failures with reasons, cost per 1,000 requests, latency percentiles, calibration, baseline diff, monthly projection.
- **Gate.** `evalsprint compare` with an exit code: pass-rate drop (`auto` by size, McNemar), `min_pass_rate`, critical tags (a target crash on a case that passed counts), cost, p95 latency, error rate, removed or edited cases, changed judges (`judges_sha`, without custom-judge code), calibration warnings; `evalsprint baseline`.
- **CI.** GitHub Actions workflows (`check-secrets`, `changes`, `evals`, `comment`, `gate`) that read the gate and the baseline from the base branch, with the suite and the comparison in one job; `EVAL_PATHS` and `REQUIRE_BASELINE`; a sticky comment; an optional `EVALSPRINT_READ_TOKEN` for a private kit; `CODEOWNERS.example`; `report --gate-config` and `compare --gate-config`.
- **Docs and demo.** ARCHITECTURE, METHODOLOGY, WINDOWS, SPRINT_PLAYBOOK; an offline demo (a simulated RAG support bot, labeled as a simulation); 1449 tests on Python 3.10 to 3.13.
