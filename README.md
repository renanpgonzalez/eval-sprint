# Eval Sprint kit

**Measure whether your LLM feature got better or worse, and what it costs, before your users tell you.**

You shipped a feature that calls an LLM. Since then someone changed a prompt, upgraded a model or re-indexed the knowledge base, and the only quality check is "it looked fine when I tried it". This kit replaces that with numbers you can defend: a test set, a judge whose reliability has been measured against human labels, a report with confidence intervals and real cost, and a CI gate that blocks regressions and says how sure it is.

It is the toolkit behind the fixed-price **Eval Sprint** service (a 2-3 week engagement, see [docs/SPRINT_PLAYBOOK.md](docs/SPRINT_PLAYBOOK.md)), and it is small enough to read in an afternoon and keep in your own repository. Python 3.10+, one runtime dependency (PyYAML), no hosted service.

## What it delivers

| Sprint deliverable | What you get | How |
|---|---|---|
| **1. Test set** | A JSONL file of cases (input, reference, expected behavior, tags, per-case checks) with validation and statistics | `cases.jsonl`, `evalsprint describe` |
| **2. Calibrated LLM judge** | A rubric-based judge with binary criteria, plus a blind labeling page for your experts and a calibration report: agreement, Cohen's kappa with CI and a decision taken on that CI, true-positive and true-negative rate, disagreements, and a judge-corrected pass rate | `evalsprint label`, `evalsprint calibrate` |
| **3. Quality and cost report** | One self-contained HTML file: pass rate with Wilson intervals, by tag, by judge, errors kept apart from failures, failing cases with reasons, cost per request from real token usage, latency percentiles, calibration, baseline diff | `evalsprint report` |
| **4. CI regression gate** | Baseline-vs-candidate comparison with an exit code, a sticky pull-request comment, and gate settings, baseline and kit that a pull request cannot loosen for itself because the comparison runs in a job that never executes its code | `evalsprint init --ci`, `evalsprint baseline`, `evalsprint compare`, `evalsprint noise`, [evalsprint/templates/github](evalsprint/templates/github/README.md) |

## Quickstart

```bash
uv venv && uv pip install -e .        # or: python -m venv .venv && pip install -e .
python examples/support_bot/run_demo.py
```

On Windows, see [docs/WINDOWS.md](docs/WINDOWS.md) (short version: `py -3.12 -m venv .venv`, then `.\.venv\Scripts\python.exe -m pip install -e .`).

The demo evaluates a small RAG support bot end to end without any API key. It runs three variants through the same suite: **v1** (generic prompt), **v2** (a grounded production prompt) and **v3** (v2 made cheaper with a smaller model and less context). It compares them with the regression gate, calibrates the judge against labels and writes a report per run.

Everything lands in `./demo_out/` (ignored by git): start with `demo_out/SUMMARY.md` (one table telling the whole story), then open `demo_out/runs/v2-grounded/report.html` in a browser to see what a client receives.

The bot and the judge run on a seeded **simulator** (`examples/support_bot/sim.py`), and the calibration labels are synthetic, so the numbers show that the pipeline works, not how any real model performs. `python examples/support_bot/run_demo.py --real` runs the same story on real models (needs `ANTHROPIC_API_KEY`).

Start a suite of your own in any repository. The templates ship inside the package, so this works from a plain `pip install` (see "Adapting the kit to a client repo"):

```bash
evalsprint init --ci                                                # evals/ (and the GitHub workflows); never overwrites without --force
evalsprint describe -c evals/eval.yaml                              # offline, no API key
JUDGE_PROVIDER=mock evalsprint run -c evals/eval.yaml --label smoke # offline too: canned answers and a placeholder judge, measures NOTHING
```

Then try the pieces by hand on the example suite:

```bash
cd examples/support_bot
evalsprint describe -c eval.yaml
evalsprint run -c eval.yaml --label v1
evalsprint run -c eval.yaml --label v2 --set target.params.prompt=v2
evalsprint compare runs/<v1-run-id> runs/<v2-run-id> -c eval.yaml      # exit 1 on regression
evalsprint report runs/<v2-run-id> --baseline runs/<v1-run-id> -o report.html
```

## Core concepts

**Case.** One test: an `id`, an `input` (string or object), and optionally a `reference` (the facts a correct answer must contain), an `expected_behavior` (`answer`, `abstain` or `refuse`), `tags`, per-case `checks` and `metadata`. Unknown fields are kept in `metadata`. One case per line in a `.jsonl` file; blank lines and lines starting with `//` are ignored. `describe` validates the file: ids must be non-empty, `tags` must be a list of strings, check types must exist.

```json
{"id": "billing-001", "input": "How do I download my invoice?", "reference": "Settings > Billing > Download.", "expected_behavior": "answer", "tags": ["billing"], "checks": [{"type": "contains", "values": ["Billing"]}]}
```

**Target.** The system under test, wrapped as a Python function `fn(input, params) -> str | dict`. Return the text, or a dict with `text` and optionally `model`, `usage` (token counts), `cost_usd`, `latency_s` and `meta` (for example the retrieved `context`). Exceptions are recorded as errors for that case and the run continues. The target never sees the reference, tags or checks. Ready-made adapters for a Python function, an HTTP endpoint and a bare prompt, plus an offline stub and an offline placeholder judge, live in [evalsprint/templates/target_adapter.py](evalsprint/templates/target_adapter.py).

**Judge.** Anything that scores an output. Deterministic judges are cheap and noise-free: `contains`, `not_contains`, `regex`, `max_chars`, `min_chars`, `json_valid`, `exact_match`, plus `custom` (your Python function) and the per-case `checks`. The `llm` judge grades against a rubric with a model. Every judge can be limited with `when_tags` or `when_behavior`. A misspelled judge key is an error, not a silent no-op.

**Rubric.** A YAML list of yes/no criteria for the LLM judge. Each has an `id`, a `question`, `critical` (default true) and `weight`. The judge writes a short reasoning and a pass/fail per criterion; the case verdict is computed in code: it passes when every critical criterion passes. Optional `samples: 3` runs the judge three times and takes the per-criterion majority (an even number of samples that ties counts as a fail). The output under test is treated as untrusted data: it sits inside delimiters with a random per-call nonce, and a heuristic flags outputs that try to instruct the judge.

**Outcome: pass, fail or error.** A case that could not be judged (the target raised, or a judge failed after its retries) is an `error`. Errors are left out of the run's own pass rate and counted on their own (`n_errors`, split into target and judge errors). A run with more than `max_error_rate` (default 5%) of errors is **unhealthy**: `evalsprint run` exits with code 3, and neither `baseline` nor the CI gate will use it. An API outage therefore reads as "infrastructure error", not as a quality collapse. One kind of error does count when two runs are compared: a **target error on a case that passed in the baseline is a failure** (the feature crashed where it used to answer; otherwise a change could turn regressions into "errors" and stay under every limit). A judge error, an error that is already in the baseline and a crash on a case that already failed are left out of the comparison, and the comparison names them. Transient crashes therefore add false alarms (exact at 5% noise: a 1% crash rate takes them from 10.6% to 14.7% at 45 paired cases and from 4.0% to 8.0% at 200): the runner calls a target that crashed again (`target_retries`: default 1, at most 5, `0` switches it off; every retry is a paid call, counted in the cost, in `n_target_retries` and, per case, in `target_retries_used`), and the adapter should retry provider errors itself. **Set `target_retries: 0` when the target is not idempotent**: a call that sends a message, writes a record or charges a card would happen twice. A run carries `placeholder: true` when its target callable is a function named `offline_stub` (the scaffold's) or when any LLM judge has the provider `mock` (read after `${VAR}` and `--set` are expanded, so `JUDGE_PROVIDER=mock` turns a run into a placeholder): its report says so, `evalsprint baseline` refuses it without `--force`, and `compare` warns when the baseline is one. A judge input longer than `max_output_chars` is not sent (the case fails, counted in `n_oversize`).

**Pass rule.** How judges combine into one verdict per case: `all` (default), `any`, the name of one judge, or a list of names that must all pass.

**Repeats.** Model outputs are not deterministic. `repeat: {n: 3, per_tag: {safety: 5}}` in `eval.yaml` runs every case 3 times and the cases tagged `safety` 5 times (a case runs as many times as the largest `per_tag` count of its tags, else `n`), and takes the majority; ties fail. `per_tag` below `n` is honoured too (`{n: 5, per_tag: {cheap: 1}}` runs the `cheap` cases once). `run --repeat N` sets `n` and keeps `per_tag`; the older `{n: 5, tags: [safety]}` still works and means `{n: 1, per_tag: {safety: 5}}`, but naming `tags` and `per_tag` together is a configuration error (exit 2). The summary reports `stability.flip_rate`, the share of repeated cases whose attempts disagree: a direct measurement of your noise floor; from 20 repeated cases on, `evalsprint noise RUN` turns it into the false alarm and the detection of the whole gate, about, under the protocol of that run. `repeat` is part of the baseline: a pull request that changes it is blocked. **Below about 150 cases repeat every case 3 times** (`repeat: {n: 3}`, which the template enables): at 5% noise and 45 cases the false-alarm rate falls from 10.6% to 0.3% and a true 10 point drop is caught 82% of the time instead of 67%, for three times the target and judge calls. **Repeat the critical cases 5 times, and only those** (`per_tag`, below): `n: 5` on every case is the expensive way to the same protection. From 150 cases on, if the target does not crash, you can delete the block. A crashed attempt of a repeated case is counted (`attempt_error_rate`) and named in the comparison even when the majority passed.

**Calibration.** You cannot trust a judge you have not measured. Experts label about 150 outputs blind (the judge's verdict is hidden, and the stratum recorded in the label file is a keyed token that only the run's own `.label_secret` can decode); `evalsprint calibrate` reports agreement, Cohen's kappa with a bootstrap CI, the judge's true-positive and true-negative rates (re-weighted for how the sample was drawn), every disagreement, and a corrected pass rate. The verdict on the judge is decided by the **lower bound of the kappa interval of the whole run** (the weighted kappa, which corrects for how the sample was drawn), not by a point estimate and not by the raw sample: `trustworthy` (lower bound at least 0.8 **and** a reliable true-negative rate: at least 10 human fails, a TNR of at least 0.75 and a narrow enough interval), `usable` (lower bound at least 0.6, with at least 40 labeled cases), `not_trustworthy`, `inconclusive` (more labels needed, and the report estimates how many, never more than the run has cases to label) or `insufficient_data` (under 30 labels). The interval is smoothed for few disagreements, so a judge that happened to agree on every label of a small sample is not certified early: with perfect agreement it is released (`usable`) at 40 labels (45 when 90% of the human labels are pass), and, when every case is labeled and the humans pass 50%, 70%, 80% and 90% of the outputs, it is `trustworthy` in at least 80% of the runs at 40, 48, 67 and 124 labels respectively (the number of human fails in a real run is random, and fewer fails need more labels). A judge that is merely good needs many more: at 100 labels one whose true-negative rate is 0.9 is called reliable in about half the samples. Save the result next to the baseline (`--json evals/baseline/calibration.json`) and the gate warns whenever the judge is uncalibrated, not released (`inconclusive`, `not_trustworthy`, `insufficient_data`) or below `min_judge_kappa`. `calibrate --export-fewshot PATH` turns the clearest disagreements into rubric examples and sets a random holdout of the labeled cases aside; `--exclude-holdout PATH` leaves them out of the next calibration so the judge is not graded on cases it was shown. **How many labels depends on how often the humans pass the output** (the decision needs human fails to judge the true-negative rate): the table in the [sprint playbook](docs/SPRINT_PLAYBOOK.md) gives the best-case budget per human pass rate, and a judge with errors needs more, so plan about 150. `tnr_reliable` is a screening flag, not a guarantee: it means the rate was measured narrowly and its estimate is at least 0.75, not that the true rate is. `calibrate` takes several label files (`--labels` repeated), a calibration remembers the `judges_sha` it was made for and the report and `compare` warn when the judges changed after it, and after a change only the changed outputs need a label when the earlier labels covered every unchanged case (a full earlier pass); after a sampled pass the export also draws unchanged cases that never had a label (`label --previous-labels`).

**Gate.** Rules applied when a candidate run is compared with the committed baseline. `compare` reports a regression, and exits with code 1, if any of these hold:

1. the pass rate dropped by more than `max_pass_rate_drop`. With the default `auto`, one rule for every test-set size: the **net loss** (cases that went pass to fail minus fail to pass) is at least `max(3, ceil(n / 50))` cases (at least 3, and 2 points from 150 paired cases on) **and** a one-sided exact McNemar test finds it significant at a level that falls smoothly from 0.24 at 45 cases to 0.0575 for large suites. There is no switch and no cliff at any size; the comparison reports `gate_mode`, `effective_min_net_loss` and `effective_alpha`. A number instead of `auto` is a fixed limit;
2. the pass rate is below `min_pass_rate`, on the whole candidate run **and** on the cases that also exist in the baseline (target errors count as failures there), so appending easy cases cannot lift it;
3. a case tagged with one of `critical_tags` went from pass to fail, including a crash of the target on a case that passed in the baseline, or passed in the baseline and the *judge* errored in the candidate (it could not be verified, so the gate fails closed). Repeat those cases 5 times, see below;
4. mean cost per case grew by more than `max_cost_increase_pct`;
5. p95 latency grew by more than `max_p95_latency_increase_pct`;
6. the error rate is above `max_error_rate`, on the whole candidate run **or** on the cases that also exist in the baseline, so added cases cannot dilute it (reported as an unhealthy run, "not a quality signal");
7. baseline cases are missing from the candidate (`max_removed_cases`, default 0) or were edited (`max_changed_cases`, default 0): deleting the cases you fail is the cheapest way to pass a gate;
8. the judges changed: a different judge block, rubric text, `pass_rule`, the source of a `custom` judge's file or any of its `data_files` (`summary.judges_sha`) is a regression reason unless `allow_judge_changes: true`, because a more lenient judge lifts every pass rate. Update the baseline in a reviewed PR;
9. with `require_calibration: true`, the LLM judge is uncalibrated, its calibration decision is not `usable` or `trustworthy` (`inconclusive`, `not_trustworthy` and `insufficient_data` all fail), or the lower bound of its **weighted** kappa interval is below `min_judge_kappa` (otherwise these are warnings). The gate reads the same weighted kappa as `calibrate`; an old `calibration.json` without it is read as unweighted, marked `legacy` and warned about;
10. the evaluation protocol changed: a different `repeat` (`n` or `per_tag`) between baseline and candidate is a regression reason unless `allow_repeat_change: true`, because a bigger majority vote is an easier gate. A different `target_retries` is a regression reason too, unless `allow_target_retries_change: true`: a retry hides a transient crash from the pass rate, so raising it can hide a crash regression (a summary that does not record it is a warning, and so is a candidate whose share of retried calls is at least `retry_share_warn`, 10 percentage points, above the baseline's; that warning is weak for small increases: against a baseline that retried 5% of its calls it fires in 0.12% of the comparisons of an unchanged target at 100 calls, in 11.2% when the candidate's calls crash 10% of the time, in 88.8% at 20% and always at 50%, so read the retry counts that `gate.md`, `gate.json` and the report show). A different version of the kit, patch included, is a warning, or a reason with `require_same_kit_version: true`.

Warnings that never trip the gate: a non-critical tag whose pass rate fell by at least `tag_drop_warning_pp` (20) points on at least `tag_drop_min_cases` (20) paired cases, a target crash in one attempt of a repeated case that passed in the baseline, an uncalibrated judge, a calibration made for another judge configuration, a baseline that is a placeholder run, a small test set. Cases are paired by id, and only when their content (`case_sha`, a hash of every field of the case except its id) is the same and the baseline has a verdict for them. A candidate target error on a case that passed in the baseline is paired as a failure (it feeds the pass-rate drop, the McNemar test, the by-tag rates and the critical tags, and is listed as `target_error_regressions`); a candidate judge error, a baseline error, and a crash on a case that already failed are left out (`excluded_errors`) and named in a warning. A crashed case has no output, so it does not feed the score, cost or latency deltas. `max_pass_rate_drop: null` switches rule 1 off; the other rules still apply. Unset limits are not checked. An explicit gate (`--gate-config`, `-c`) is never mixed with the gate stored in the candidate run. Details in [docs/METHODOLOGY.md](docs/METHODOLOGY.md).

**What the PR comment prints from the run's files.** Every value that comes from a run artifact (case ids, tags, run ids, kit versions, `judges_sha`, the judge's name and its calibration decision) is printed in a code span in `gate.md`, with URLs, `@mentions`, issue references and HTML entities made inert, so a hostile tag name in a pull request's own `summary.json` cannot notify anyone or plant a link: the engineering review's hostile payloads, extended to 48 values on 29 surfaces (1392 cells), gave 0 findings, against 103 before the fix. That is about markup, not about truth: the values are still written by the pull request's code, and `gate.json` and the CLI keep the plain text.

## What the gate is, and what it is not

**It is** a regression detector against a reviewed reference: on every pull request that touches LLM code it runs a fixed test set, compares the result with the committed baseline and blocks the merge when the pass rate, a critical case, the cost, the latency or the error rate got worse, when baseline cases were removed or edited, or when the judges, the rubric, the `repeat` protocol or a custom judge's source changed. The gate settings, the baseline and the kit that compares come from the **base branch**, in a job that never runs the pull request's code, and every way the pipeline can break (no key, no baseline, a failed job, a missing artifact) ends as a red check, never as a silent pass.

**How it decides, in one paragraph.** The gate compares each change with the committed baseline on the same cases. It blocks the change only when the cases that went from pass to fail outnumber those that went from fail to pass by at least max(3, n/50), and a one-sided exact sign test (McNemar) says that such an imbalance would be unusual by chance. The test is lenient on small suites (alpha about 24% at 45 cases, 12% at 100, 7% at 150) and tightens to about 5.8% beyond roughly 300 cases. It is a noise-aware threshold, not a guarantee. With 5% random noise per case and one attempt per case, an unchanged system is blocked about 11% of the time at 45 cases, 7% at 100 and 4% at 200, averaged over possible baselines; for one committed baseline the rate can be far higher or lower. A 10-point drop is caught about 67%, 80% and 93% of the time, and a 5-point drop only about 39%, 42% and 51%. Cases tagged critical sit outside this statistical rule: any single pass-to-fail flip blocks, so they must be repeated 5 times.

**What that paragraph leaves out** (the next section has the sizes and the crash and baseline numbers). The rates above are rounded: exactly, an unchanged system is blocked 10.6%, 7.1% and 4.0% of the time at 45, 100 and 200 cases, and a 10 point drop is caught 66.6%, 79.7% and 92.7% of the time. The false alarm is not flat: it peaks at 12.3% near 54 cases (15.1% with 10% noise), and between 60 and 149 cases the rule of v0.1 had a lower false alarm and a higher detection at 84 of the 90 sizes at 5% noise (every size except 60 to 62 and 78 to 80 cases; at 10% noise v0.2 is the stricter rule and blocks less often: over those sizes the mean false alarm is 8.3% against 11.5% and the mean detection of a 10 point drop 61.2% against 72.9%, v0.2 against v0.1), so the current rule is one smooth rule, not a better one at every size. The 4% at 200 cases holds only if the target does not crash (a 1% crash rate doubles it). And the committed baseline is one noisy draw: the chance that it leaves more than 15% of later unchanged pull requests blocked is 28.8%, 14.0% and 7.2% at 45, 100 and 200 cases. `evalsprint noise RUN` prices the whole gate (the pass-rate rule and the critical-case rule together) for the repeat protocol of a run, from the flip rate of its repeated cases, and prints "about" figures: it assumes that the noise measured on the repeated cases is the noise of every case, and it needs at least 20 repeated cases (with fewer it prints "not estimated" and no rate, which is what the 10 cases of the `evalsprint init` scaffold give: repeat every case of a suite of 20 or more cases with `run --repeat 3`, or use the tables).

**Two more measured sentences, for a suite with critical cases and for a target that crashes** (exact, at 5% noise per attempt; `scripts/gate_numbers.py`). With 8 critical cases in a 45-case suite, an unchanged change is blocked 36.67% of the time with one attempt per case, 5.79% with every case repeated 3 times, and 1.11% with every case 3 times and the critical ones 5 times (`repeat: {n: 3, per_tag: {safety: 5}}`); repeating every case 5 times alone gives 0.92% and costs more. A target that crashes on 5% of the calls makes an unchanged 100-case change blocked in 54% of the runs (38% of all runs are unhealthy and never compared); one retry inside the run (`target_retries: 1`, the default) brings it to 8%. The same retry also hides a candidate that starts to crash on some calls: with `target_retries: 1` and 100 cases, one whose target crashes on 10% of its calls is blocked in 11% of the runs and one that crashes on 20% of its calls in 39%, against 7% for an unchanged candidate. The gate now blocks a change of `target_retries`, prints the retries of both runs and warns when the candidate retried at least 10 percentage points more of its calls than the baseline, but that warning is weak for small increases (against a baseline that retried 5% of its calls it fires in 11 of 100 comparisons for a candidate that crashes on 10% of its calls and in 89 of 100 for 20%), so the crash and retry counts of the report must still be read next to the gate.

**It is not** proof that the feature is good (only "not worse than the baseline, on these cases, as graded by this judge"); **not a check that the candidate results are genuine** (the PR's own code produces them, so a change that returns canned answers or a judge that always passes gets through: only review catches that); not a replacement for code review (the workflow file, the adapter and new cases that only look easy are invisible to it: CODEOWNERS is part of the gate); not sensitive on a small test set (next section); and not a prompt-injection defense (the judge's `injection_suspected` hint found 43% of injection attempts and flagged 27.5% of legitimate text when the independent review measured evalsprint 0.1; the heuristic is unchanged). The full statement is in [evalsprint/templates/github/README.md](evalsprint/templates/github/README.md).

## How many cases do you need? What the gate can and cannot catch

Be honest with yourself and the client about this before choosing a test-set size. The table comes from an exact calculation (baseline pass rate 80%; each case's verdict flips with the stated probability in every run, independently, even for an identical system), under the default `auto` gate with one attempt per case. **False alarm** is an unchanged system being blocked; **caught** is a true drop being blocked. The 5% noise level is an assumption: run `evalsprint run --repeat 3`, read `stability.flip_rate` and run `evalsprint noise RUN` on it to get "about" figures for the whole gate of your own suite and protocol (it needs at least 20 repeated cases: the 10 cases of the `evalsprint init` scaffold give "not estimated", so grow the suite first, or keep the table).

| Paired cases | False alarm at 2% / 5% / 10% noise | True 5 p.p. drop caught | True 10 p.p. drop caught | True 15 p.p. drop caught |
|---:|---|---:|---:|---:|
| 45 | 3.0% / **10.6%** / 14.7% | 39% | 67% | 85% |
| 100 | 3.4% / 7.1% / 8.3% | 42% | 80% | 96% |
| 200 | 2.4% / 4.0% / 4.5% | 51% | 93% | 99.6% |
| 400 | 2.7% / 4.1% / 4.6% | 78% | 99.7% | 100% |

- **A 45-case set is a smoke test.** It reliably catches only large regressions (about 85 in 100 of a 15 point drop, 2 in 3 of a 10 point drop), and an unchanged system is still blocked roughly once in nine runs at 5% noise. The PR comment says so when fewer than 100 cases are paired.
- **Below about 150 cases, repeat every case 3 times.** `repeat: {n: 3}` (enabled in the template) takes the majority of three attempts: at 45 cases and 5% noise per attempt the false-alarm rate falls from 10.6% to **0.3%** and the detection of a 10 point drop rises from 66.6% to **81.6%**; at 100 cases, from 7.1% to 0.3% and from 79.7% to 97.5% (exact, assuming independent attempts: noise that is the same on every attempt of a case is not reduced). It costs three times the target and judge calls. At 30 cases it cuts false alarms but does not help a 5 point drop: that set is too small for any gate. From 150 cases on, one attempt holds false alarms at or under 5% if the target does not crash (see below): then delete the block.
- **100 to 200 cases is the practical target for a sprint.** At 5% noise false alarms are 7.1% at 100 cases and 4.0% at 200 with one attempt, and a 10 point drop is caught 80% to 93% of the time. A 5 point drop is still caught about half the time; reliable sensitivity to 3 to 5 points needs several hundred paired cases, or repeats. The curve is not perfect: false alarms peak at 12.3% near 54 cases (15.1% at 10% noise), and between 60 and 149 cases the rule is a different trade from the one in evalsprint 0.1, not a strict improvement: the old rule had a lower false alarm and a higher detection of a 10 point drop at 84 of those 90 sizes at 5% noise, while at 10% noise v0.2 is the stricter rule and blocks less often (section 9 of the workflow README has the numbers).
- **"At most 5% from 150 cases on" assumes the target does not crash.** A crash on a case that passed in the baseline counts as a failure: at 5% noise a target that crashes on 1% of the cases takes the false alarm from 4.0% to 8.0% at 200 cases (10.6% to 14.7% at 45, 7.1% to 11.1% at 100), and on 5% of the cases to 34.6%, 36.2% and 42.4%. More than `max_error_rate` (5%) of errors is an unhealthy run that is never compared.
- **The committed baseline is a lottery ticket.** The table averages over the baselines you could have drawn; the one you commit is a single noisy run, and every later pull request meets it. Given the baseline the false alarm is exact and varies: the chance that it makes more than 15% of later unchanged pull requests fail is 28.8% at 45 cases, 14.0% at 100 and 7.2% at 200 (median baseline 7.0%, 1.3% and 0.6%). Build the baseline with the same `repeat` protocol as the pull requests, which shrinks the noise of the draw, and do not re-draw it until the pull requests pass.
- **Critical tags are not statistical.** One flipped case blocks the pull request, so 8 critical cases at 5% noise per attempt would block about a third of unchanged PRs (32% on the critical rule alone, 36.67% for the whole gate at 45 cases). Repeat them, and only them: `repeat: {n: 3, per_tag: {safety: 5}}` runs every case 3 times and the critical cases 5 times. The majority of five attempts blocks **0.92%** of unchanged PRs on the critical rule (5.6% with a majority of three), while a critical case that really broke and fails 80% of its attempts is still caught **94%** of the time. The whole gate at 45 cases with 8 critical ones (the pass-rate rule and the critical rule together, computed exactly over their joint distribution) blocks **1.11%** of unchanged PRs with that protocol, against **5.79%** with `repeat: {n: 3}` on every case (`n: 5` on every case would be 0.92% but costs five times the whole suite). `compare` warns when critical cases ran fewer than five times and recommends the `per_tag` line. Unanimity of three was rejected: 0.10% false alarms, but it catches that broken case only 51% of the time.
- **The judge is usually the largest source of noise.** Use `samples: 3` on any LLM judge that gates a merge, and calibrate it before trusting the pass rate.

## Adapting the kit to a client repo

1. **Scaffold and wire the adapter.** From the client repo run `evalsprint init --ci`. It writes `evals/eval.yaml`, `rubric.yaml`, `cases.jsonl` (from the example set), `target_adapter.py` and `requirements.txt` (the kit pinned to the version that wrote it), plus, with `--ci`, `.github/workflows/evals.yml`, `evals-baseline.yml` and `.github/CODEOWNERS.evals.example`. Nothing that already exists is overwritten without `--force`. The scaffold passes `evalsprint describe -c evals/eval.yaml` and runs offline out of the box (`JUDGE_PROVIDER=mock evalsprint run -c evals/eval.yaml` uses canned answers and a placeholder judge: the pipeline works, nothing is measured, and such a run must never become a baseline). In `target_adapter.py`, pick the adapter that fits (`call_function`, `call_http`, `call_llm`) and make it call the production code path. Return token usage and retrieved context. Run `evalsprint run -c evals/eval.yaml --limit 3` with the real judge to check it.
2. **Build the test set from production logs.** Start from real, anonymised inputs, add reported failures and known-hard categories (out of scope, prompt injection, multi-part), tag everything. Aim for **150 cases or more**; 100 is the practical floor and 45 behaves like the smoke test above (keep `repeat: {n: 3}`, with `per_tag: {<critical tag>: 5}` for the critical cases, until you have about 150). `evalsprint describe -c evals/eval.yaml` validates the file and shows the tag and behavior mix. Split tags into groups (`tag_groups`: type, topic) so the report does not mix them.
3. **Write the rubric.** Turn "what good means" into yes/no questions, one failure mode each, with what a fail looks like in the client's own words. Add cheap deterministic judges for hard requirements. See [evalsprint/templates/rubric.yaml](evalsprint/templates/rubric.yaml).
4. **Run, then label about 150 outputs.** `evalsprint run -c evals/eval.yaml --label first` (if it is interrupted, `evalsprint run -c evals/eval.yaml --resume runs/<id>` continues without paying for the finished cases again), then `evalsprint label runs/<id> --sample 150 -o labeling.html` (add `--judge quality` to sample around one judge's verdict; the right number of labels depends on how often your experts pass the output, see the playbook). The expert opens the page, labels pass/fail with keyboard shortcuts, and downloads `labels.jsonl`. `evalsprint init` already put `.label_secret` and `runs/` in the client's `.gitignore`; check that they are there.
5. **Calibrate.** `evalsprint calibrate runs/<id> --labels labels.jsonl --md calibration.md --json calibration.json`. Read every disagreement, fix the rubric (`--export-fewshot examples.yaml` turns the clearest ones into rubric examples and sets a holdout aside; calibrate again with `--exclude-holdout examples.yaml`), re-run, repeat until the decision is `usable` or `trustworthy`, or you know exactly what the judge cannot grade. `inconclusive` is a legitimate result: it means the labels cannot tell a good judge from a mediocre one yet. Then `evalsprint report runs/<id> --labels labels.jsonl -o report.html`.
6. **Set the gate.** Freeze the reference with `evalsprint baseline runs/<id> --to evals/baseline`, copy `calibration.json` into it, and commit both. Agree `critical_tags` (and repeat those cases 5 times with `repeat.per_tag`), `min_pass_rate`, and any cost or latency limits with the client and write them in the `gate:` block of `eval.yaml`. `evalsprint history runs -o history.html` draws the pass rate and cost of every run and marks where the judges changed.
7. **Install CI.** Copy `.github/CODEOWNERS.evals.example` to `.github/CODEOWNERS` with the client's team, add the provider key as a secret (and, for a private kit, read the section on the `EVALSPRINT_READ_TOKEN` first: the job that runs the pull request's code can read that token while it installs the requirements, so a kit that must stay private is vendored as a wheel instead), require the **LLM evals gate** check and code-owner review (see [evalsprint/templates/github/](evalsprint/templates/github/README.md)). The workflow reads the gate, the baseline and the kit pin from the pull request's *base* branch and does the comparison in a job that does not run the PR's code, so a PR cannot loosen its own gate or patch the code that judges it (it can still fake its own results: review is the control for that), and it reports infrastructure errors apart from regressions. List your prompt and LLM code folders in `EVAL_PATHS` (pull requests that touch none of them skip the paid run and the gate passes with a note; there is deliberately no `paths:` filter, which would leave a required check pending forever), and once the first baseline is merged set `REQUIRE_BASELINE: "true"` so that a lost baseline fails the gate instead of switching it off. Agree with the client what may be committed and how long artifacts are kept: the run artifacts and the baseline contain real inputs and outputs (see the data-handling section of the workflow README). Prove it with one deliberate regression (a clear one, 10 points or more) that is blocked, and one unchanged pull request that passes; then tell the client the false-alarm rate from the table above, with its caveats (the peak of 12.3% in the middle of the range, a baseline that may be an unlucky draw, crashes that add to the rate), because an unchanged PR will occasionally be blocked and the answer is to re-run it, not to loosen the gate.

The [sprint playbook](docs/SPRINT_PLAYBOOK.md) has the kickoff questions, week-by-week plan, acceptance criteria and handover checklist.

## CLI reference

```
evalsprint [--version] [--debug] <command> ...
evalsprint init      [DIR] [--ci] [--force]                 # scaffold evals/ (and the GitHub workflows with --ci) from the packaged templates
evalsprint describe  -c eval.yaml
evalsprint run       -c eval.yaml [--label L] [--set k=v ...] [--tags t1,t2] [--limit N] [--out DIR] [--quiet] [--no-report] [--repeat N] [--resume DIR [--retry-errors]]
evalsprint noise     RUN [--gate PATH | -c eval.yaml]       # about-figures for the whole gate under THIS run's protocol, from its measured flip rate (needs 20+ repeated cases)
evalsprint compare   BASELINE_RUN CANDIDATE_RUN [-c eval.yaml | --gate-config PATH] [--md out.md] [--json out.json]   # exit 1 on regression
evalsprint report    RUN [--baseline RUN] [-c eval.yaml | --gate-config PATH] [--labels labels.jsonl] [--judge NAME] [--monthly-requests N] [-o report.html]
evalsprint history   RUNS_DIR [-o history.html] [--suite NAME]   # one page with the trend of every run
evalsprint calibrate RUN --labels labels.jsonl [--labels more.jsonl ...] [--judge NAME] [--md out.md] [--json out.json]
                     [--export-fewshot PATH [--fewshot-max N] [--holdout-frac F]] [--exclude-holdout FILE]
evalsprint label     RUN [-o labeling.html] [--csv] [--sample N] [--seed S] [--no-stratify] [--judge NAME] [--previous-labels FILE ...]
evalsprint baseline  RUN --to evals/baseline [--force]      # copy a run to be the committed baseline
```

Exit codes: `0` ok, `1` regression (`compare`), `2` usage or configuration error, `3` unhealthy run (`run`, when the error rate is above `max_error_rate`, counted per case or per attempt, so the attempt error rate also counts: a repeated case whose majority vote stands cannot hide crashed attempts; the files are still written; `baseline` also exits 3 for an unhealthy or a placeholder run), `130` interrupted (Ctrl-C) and `143` terminated (`SIGTERM`: a CI cancel, `kill`, a container stop), both after the attempts that were running were saved and with the `--resume` command on stderr. `python -m evalsprint` is equivalent to `evalsprint`. `--debug` shows the full traceback instead of a one-line error; `--version` prints the version.

- `run --repeat N` sets `repeat.n` (every case N times, majority decides) and keeps `repeat.per_tag`; `--no-report` skips `report.html`. `run --resume DIR` continues an interrupted run: it reuses the finished attempts of `DIR/results.partial.jsonl` (or of a finished `results.jsonl`) whose case and run fingerprint are unchanged, runs only the rest, and writes a **new** run with `summary.resumed_from`; the reused cost stays counted as spent. The fingerprint is the judges (configuration, rubrics, custom-judge code and `data_files`), the target (callable, `params`, and `target.source_sha`, a short hash of the **one file** the callable lives in) and the repeat protocol. **Edits in the modules that file imports are not detected**: after changing those, start a fresh run. When the fingerprint differs nothing is reused, and `summary.resumed_from.fingerprint_mismatch` says which part changed (`judges_sha`, `target`, `target_source`, `repeat`). `--retry-errors` also runs again the reusable records that ended in a provider error and the crashed attempts inside repeated cases that otherwise finished (`resumed_from.retried_errors` counts the attempts that run again). A run that stops midway, on Ctrl-C (exit 130) or `SIGTERM` (exit 143), drains, keeps what it has and prints the exact command to continue it (it prints it when the final save fails, too). `--resume` holds a lock on the run folder, the file `.resume.lock`, which exists only while a resume is running: a second concurrent resume of the same folder exits 2, and a `.resume.lock` left behind by a `kill -9` is harmless (the lock belongs to the process, not to the file).
- `noise RUN [--gate PATH | -c eval.yaml]` prices the **whole gate** for the repeat protocol the run really used: the pass-rate rule, the critical-case rule and the two together, for the attempts of every scored case and the cases that carry a critical tag. It recounts the flip rate of the repeated cases from the scored cases (so it can differ slightly from `summary.stability.flip_rate`), converts it to the noise of one **attempt**, gives each case the noise of the majority of its own attempts, and prints "about" figures: the false alarm of the whole gate and of each rule alone, the detection of a 5 and a 10 point drop (the whole gate, and the pass-rate rule alone), the spread of the baseline lottery and the gate in a paragraph. The gate is the one stored in the run unless `--gate PATH` (the file `compare` reads in CI; `--gate-config` is the same flag) or `-c eval.yaml` names another, and the output says which one it used and which tags are critical. **It needs at least 20 repeated cases.** With fewer it prints `not estimated`, the flip rate it saw and the fix (`run --repeat 3`, and `per_tag` for the critical cases), and no rate, because one case that flips or not moves the flip rate by 5 points or more: the 10 cases of the scaffold from `evalsprint init` therefore give `not estimated`, so grow the suite to at least 20 cases, every one repeated, before asking, or use the tables of this README. With nothing repeated it says so and asks for `run --repeat 3`. When no repeated case flipped it prices the figures at the upper 95% bound of the noise and says so (a flip rate of 0 from 20 cases still allows a flaky suite). **It assumes that the noise measured on the repeated cases is the noise of every case** (a case that ran once is priced at the noise of one attempt), that cases and attempts are independent and that a true drop of d points lowers every case in probability (for an exact number of broken cases the detection is from 2.4 points lower to 7.9 points higher), so read every figure as "about". An even number of attempts counts a tie as a fail: the figures price that exactly, but keep an odd `n` (3, 5). It takes the suite's pass rate from the run itself (80% when the run has none) and needs no labels and no API key.
- `init` never overwrites a file that exists (it says `kept`) unless `--force`; `init --ci` also writes `.github/CODEOWNERS.evals.example`. `history` reads every finished run directly under `RUNS_DIR` and draws the pass rate (with its band) and the cost per 1k requests, marking where `judges_sha` changed because the numbers on the two sides are not comparable.
- `compare -c eval.yaml` applies that file's `gate:` (defaults for what it omits). `compare --gate-config PATH` takes the gate **only** from that YAML's `gate:` and wins over `-c`; CI passes the base branch's copy. With either flag the gate stored in the candidate run is ignored, never mixed in. `compare` also loads `<baseline>/calibration.json` when it exists. (`report` accepts `--gate-config` too, with the same meaning.)
- `baseline` refuses an unhealthy run (errors above `max_error_rate` per case or per attempt: `run` exits 3 for the same reason) and a placeholder run (`summary.placeholder`) unless you pass `--force` (do not), and copies `calibration.json` when the run directory has one. It **warns, without refusing,** when the run covers only part of the suite (`--limit`, `--tags` or ids: `summary.selection.limited` is true), because a candidate run of the whole suite meets that baseline on only those cases and every other case shows up as a new case in every comparison; a run whose `summary.json` does not record `selection` (written by an older evalsprint) gets a warning that its coverage is unknown. Build the baseline from a run without `--limit` or `--tags`. A misspelled top-level key in `eval.yaml` is an error (exit 2), not a silently ignored setting.
- A `summary.json` that was edited so that a number is text (or a list) makes `report`, `compare` and `baseline` stop with a one-line error that names the field (`the field 'pass_rate' should be a number but is 'x<b>'`, the value cut and made inert) and with the exit code the command already used, instead of a Python traceback. `compare` decides from the records in `results.jsonl`, not from those summary fields.
- `label --judge NAME` samples around that judge's verdict; `--no-stratify` samples at random. `label --previous-labels FILE` (repeatable) leaves out the cases whose current output already has a label in that file, so after a change only the changed outputs need a label when the earlier labels covered every unchanged case (a full earlier pass); after a sampled pass the export also draws unchanged cases that never had a label (labeling only the changed outputs after a sampled pass biases the true-negative rate). `calibrate --labels` may be repeated: the files are read as one. `report --monthly-requests N` adds a monthly cost projection.

A run is a directory `runs/<run_id>/` with `results.jsonl` (one record per case, in dataset order) and `summary.json`. Every command that takes `RUN` accepts that directory. Commands write their files before printing, and stdout is tolerant of legacy console encodings (see [docs/WINDOWS.md](docs/WINDOWS.md)).

`--set key.path=value` overrides any `eval.yaml` key for one run; values are parsed as YAML and list items are addressed by index:

```bash
evalsprint run -c eval.yaml --set target.params.prompt=v2 --set concurrency=2 --set judges.2.value=600
```

(In the bundled demo, judge 2 is the `max_chars` guardrail named `length`, so this lowers its limit from 1200 to 600. Judge 0 is the LLM judge, which has no `value` key: a misspelled or misplaced key is rejected as unknown, never ignored.)

`${VAR}` and `${VAR:-default}` are expanded anywhere in `eval.yaml`, so one file can switch providers per environment (`provider: "${JUDGE_PROVIDER:-anthropic}"`). A value that is only a variable becomes a number or boolean only when it is strictly one (`8`, `0.5`, `true`); everything else, including `0123` and `no`, stays a string. Relative paths are resolved against the folder that contains `eval.yaml`.

| Key | Meaning |
|---|---|
| `suite`, `dataset` | Name shown in reports; path of the cases file |
| `target.callable`, `target.params` | `file.py:function` or `package.module:function`; dict passed to it on every call |
| `judges` | List of judges (`type`, optional `name`, `when_tags`, `when_behavior`, plus type-specific keys; the `llm` judge also takes `max_output_chars` and `max_section_chars`, default 20000; a `custom` judge takes `data_files`, the files it reads, which count as part of the judge for `judges_sha`) |
| `pass_rule` | `all` (default), `any`, a judge name, or a list of names |
| `repeat` | `{n: 3}`: every case 3 times (the template default, for suites under about 150 cases); `{n: 3, per_tag: {safety: 5}}`: and the safety cases 5 times (the recommended shape when you have critical tags). A case runs the largest count of its tags, else `n`; majority decides. `per_tag` below `n` is honoured. The old `{n: 5, tags: [safety]}` means `{n: 1, per_tag: {safety: 5}}`; `tags` and `per_tag` together are an error. Part of the baseline |
| `target_retries` | Times a target call that errored is tried again inside the run (default 1, at most 5, 0 = off) before it counts as an error. Retries are paid calls and counted; use 0 for a target that is not idempotent |
| `tag_groups` | `{type: [answerable, ...], topic: [...]}`: one report table per group |
| `behaviors` | Optional list of allowed `expected_behavior` values, validated at load |
| `concurrency` | Cases in flight at once (default 4); results keep dataset order |
| `gate` | Regression thresholds, merged with the defaults (all 19 keys in `evalsprint/templates/eval.yaml`; `allow_judge_changes`, `allow_repeat_change`, `allow_target_retries_change` and `max_removed_cases` are the ones that protect the test set, the judges and the protocol) |
| `pricing` | Per-model price overrides, USD per 1M tokens |
| `runs_dir` | Where runs are written (default `runs/` next to `eval.yaml`) |

## Design principles

- **Binary criteria, not 1-10 scores.** Pass/fail per criterion is easier for a human to agree with, so the judge can actually be calibrated, and it is far more stable from run to run.
- **The verdict is computed in code, not by the model.** The judge answers small yes/no questions with reasoning; whether a case passes follows from which criteria are critical, so every verdict is traceable and auditable.
- **An error is not a failure.** If the grader is down, the run is unhealthy, not the feature.
- **Wilson confidence intervals.** Test sets have dozens to a few hundred cases, where the textbook interval misbehaves near 0% and 100%; Wilson stays honest and shows how much a pass rate can move by chance.
- **McNemar's exact test for paired regressions.** Baseline and candidate run on the same cases, so only the cases that flipped carry information, and the one-sided exact test on those flips tells you whether "it got worse" is more than noise.
- **The judge is measured, and the decision uses the interval.** Horvitz-Thompson weights undo the stratified labeling sample; the Rogan-Gladen correction uses the measured true-positive and true-negative rates, and refuses to correct a judge that is no better than chance.
- **The gate cannot be edited by the change it judges, but it can be fooled by results the change writes.** Gate settings, baseline and the kit that compares come from the base branch, in a job that never runs the pull request's code; removed or edited cases and changed judges, rubrics, custom-judge source and `data_files`, or `repeat` protocol are counted. What it cannot see (the authenticity of the candidate results, the code of the target and what a `custom` judge imports, the coverage of the test set, the workflow files) is protected by code-owner review, which is why `CODEOWNERS` is part of the setup and not an extra.
- **Cost from real token usage.** Estimates from prompt length are off by a lot; usage returned by the API (including cached tokens) times a price table gives the number a finance team will actually recognise.
- **Standard library only (plus PyYAML).** It installs into any client's CI without dependency conflicts, and the whole statistics layer fits in one readable file you can explain to a client.

## Limits, stated plainly

- The kit measures; it does not improve the feature. It shows where and how often it fails, and tells you within error bars whether a change helped.
- **The gate is a noisy instrument.** With 45 cases and one attempt per case it blocks an unchanged system about once in nine runs and misses a 5 point drop more than half the time (repeating every case 3 times brings that to 3 in 1000, if the attempts are independent); with 100 to 200 cases it blocks 4 to 7 in 100 and catches a 10 point drop 80% to 93% of the time (at the assumed 5% noise). The false alarm peaks at 12.3% near 54 cases (15.1% at 10% noise); "at most 5% from 150 cases on" holds only if the target does not crash (a 1% crash rate doubles it at 200 cases); and the committed baseline is one noisy draw (the chance that it leaves more than 15% of later unchanged pull requests blocked is 28.8%, 14.0% and 7.2% at 45, 100 and 200 cases). Between 60 and 149 cases the gate of v0.1 was better at 84 of 90 sizes at 5% noise (at 10% noise v0.2 is the stricter rule). Do not promise a client "no false alarms", or a false-alarm rate for one pull request.
- **`evalsprint noise` is a model of your suite, not a measurement of its false alarm.** It prices the whole gate for the protocol of the run it reads, in "about" figures, and it needs at least 20 repeated cases (the 10 cases of the `init` scaffold give "not estimated"). It assumes that the noise measured on the repeated cases is the noise of every case and that cases and attempts are independent; a suite where a few flaky cases carry most of the flips is not what it models, and a flip rate of 0 is priced at the upper 95% bound, not at zero. Hand over its figures together with the flip rate and these assumptions, never as "your suite's false-alarm rate".
- **`target_retries` does not make crashes harmless, and the gate does not show every crash.** A retry hides a transient crash from the pass rate and from the error rate. The gate blocks a changed `target_retries`, prints the retries of both runs (`gate.md`, `gate.json`) and warns when the candidate retried at least 10 percentage points more of its calls than the baseline, but that warning is weak for small increases: against a baseline that already retried 5% of its calls it fires in 0.12% of the comparisons of an unchanged target at 100 calls, in 11.2% when the candidate's calls crash 10% of the time, in 88.8% at 20% and always at 50%. With the default retry a target that crashes on 10% of its calls is blocked in 11% of the runs (an unchanged one, 7%). A crash on a fixed 10% of the cases is blocked at any `target_retries`, because the run is unhealthy. Read the crash and retry counts of every comparison.
- **The tag-drop warning does not cover small tags.** A non-critical tag with fewer than `tag_drop_min_cases` (20) paired cases never warns: with 10 as the minimum, a comparison of 10 tags of 10 cases with no change raised a spurious warning in 43.4% of the runs at 5% noise, and with 20 it is 0%. Even at 20, five tags of 20 cases raise a spurious warning in 3.3% of the unchanged comparisons at 5% noise and in 14.8% at 10%. It is a warning, never a reason.
- **"After a change, only the outputs that changed need a label" is true only when the earlier labels covered every unchanged case** (a full earlier pass). After a sampled pass `label --previous-labels` also draws the never-labeled unchanged cases; if the humans label only the changed outputs there, the true-negative rate is biased by about 6 to 7 points (the review's simulation: 300 cases, 20, 40 or 80 new labels).
- **The candidate results come from the pull request's own code.** The comparison, the gate settings, the baseline and the kit are out of its reach; a change that fakes its results is not. Review is the control, and the workflow file itself is protected only by CODEOWNERS.
- An LLM judge is only as good as its measured agreement with your experts. Report the calibration numbers, including the decision (`usable`, `inconclusive`, ...), next to every pass rate you quote. With about 100 labels even a judge whose true kappa is 0.72 is certified `usable` less than half the time.
- The true-negative rate is measured precisely enough (`tnr_reliable`) only with enough human fails: never at 40 or 60 labels, and at 100 labels in 2% to 98% of the samples for a judge whose true TNR is 0.7 to 1.0, so plan about 150 labels (more when the humans pass 90% or more of the outputs). A judge that agrees with every label is `trustworthy` in at least 80% of the runs only from 40, 48, 67 and 124 labels at 50%, 70%, 80% and 90% human pass respectively: that is the floor, not the plan. `tnr_reliable` is a screening flag, not a guarantee that the true rate is at least 0.75: a judge whose true rate is 70% still passes it in 2% to 28% of simulated runs.
- Judge hardening against prompt injection is structural and unit-tested. Its behavior against real models under attack has not been tested, and `injection_suspected` is a hint (43% recall and 27.5% false positives, measured on evalsprint 0.1), not a defense.
- The demo runs on a simulator. Its numbers show the pipeline works, not how any model performs.
- **The job that runs the pull request's code can read your kit's read token** while it installs the requirements (it is a dependency of the pull request, and so is code from it). Keep the token read-only and limited to the kit repository, or vendor the wheel of the kit in `evals/vendor/` and give that job no token (workflow README, section 2).
- The CI workflows were run by an emulator against stubs, not on a GitHub-hosted runner (artifact hand-over between the jobs and job isolation are emulated, not observed), and the Windows guidance was not run on Windows. Check the first real pull request and the first Windows run.
